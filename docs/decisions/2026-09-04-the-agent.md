# The agent

2026-09-04

The first slice of the agent, end to end: a conversation on the person's
machine, streamed to the page and kept in the database, metered per org
through a gateway, picked up again by id after a reload or a restart.

**The harness is Claude Code through the ACP adapter.** The interface is an
ACP client, as the field guide says, and `@agentclientprotocol/claude-agent-acp`
is the ACP organisation's own adapter over the Claude Agent SDK: it loads a
session from its transcript, takes a gateway through `providers/set`, takes
MCP servers at `session/new`, and switches to `bypassPermissions` when asked,
which as root needs `IS_SANDBOX=1`. Driving the SDK directly, as t3code does,
was rejected: the interface would not be an ACP client. Zed's older
`claude-code-acp` is this adapter's predecessor.

**One harness process per conversation**, spawned by the daemon inside the
operating system on the volume, as root, at home, with full freedom: whatever
still asks for permission is allowed. The transcript lands in `~/.claude`
on the volume. The harness ships in the image with the daemon's dependencies
and `/computer` is bound into the OS at boot, so a new image is a new
harness and the OS stays the person's. On a laptop the same file runs from
`apps/computer/node_modules` with the fake machine's directory as home.

**Models are reached through a gateway in the app.** The machine holds no
vendor key. The adapter points Claude Code at `/model` on the app with the
machine's own secret; the app swaps the vendor's key in, streams the answer
back, and reads every call's tokens off the events as they pass. Metering
happens where the money is spent, the abuse cap is enforced at the door, and
a person with root on their machine cannot read the org's key. Rejected:
handing the key to the machine and trusting its report of what it used; the
field guide already refuses to let a machine's word buy it room.

**Any model that speaks the Anthropic protocol; one offered for now.**
OpenRouter serves its whole catalogue over that protocol, so it is a route in
the same gateway: a bare Claude id would go to Anthropic, a `vendor/model` id
goes to OpenRouter, each with its own key. The catalogue offers one model,
`z-ai/glm-5.3-flash`, and the gateway refuses a call naming any other before
it costs: the harness sends tens of thousands of tokens of its own with every
call, so the price per token is the whole bill, and a first try on Claude
Opus 5 through OpenRouter spent $0.30 on a stray keystroke. The daemon pins
the harness's side calls (its summaries and subagents) to the same model. The
person picks from what is offered in the composer; a change between turns is
a new harness process on the same transcript. OpenRouter is asked for each
call's exact price afterwards, and the meter takes that over the list price.

**The vendor's cache is used, and the meter shows it.** Z.AI caches a
prompt's repeated prefix on its own, with no breakpoints to place, and bills
a cached token at a fifth of the price; the harness's usage figures do not
show it, the gateway's do, read from every answer. The gateway tells
OpenRouter which conversation a call belongs to (`x-session-id`), which is
how OpenRouter keeps one conversation's calls on one upstream cache rather
than routing by the first messages, which an agent rewrites. The composer's
meter says what share of a conversation's tokens the cache served, so a
model that stops caching is seen, not suspected. The first call after a
long pause misses: the vendor's cache expires, and it is not ours to hold.

**A session is configured by the app in one answer.** The daemon asks
`/agent/bootstrap` with the session's id and gets back the model, the
gateway, the MCP servers and whether the agent is faked. Adding a vendor, a
model or a tool is a change in `apps/web` alone; the brain as an MCP server
is the first entry that list will carry.

**The conversation lives in the database; the record of what is running
lives on the volume.** The daemon posts every finalised event to
`/agent/report` as the machine, in order, retrying a batch that failed;
`agent_events` is what the page renders, `agent_sessions` what the sidebar
lists. `~/.placeholder/sessions.json` maps our session id to the harness's,
with the model and whether a turn was in flight, and is what a boot reads:
a session cut off mid-turn is told so, loaded from its transcript, and told
to carry on. That directory is the daemon's, hidden from the disk like
`lost+found`.

**A turn the agent begins itself is a turn.** The harness wakes on its own:
from a wakeup it scheduled, a cron it set, a task that came back. Over ACP
nothing announces that; words simply arrive with no prompt of ours pending.
The daemon opens a turn on the first of them, recorded as a `wake` with the
reason the harness gave when it asked to be woken, and closes it on the one
signal the adapter does send at the end of a cycle, the usage update that
carries the cycle's cost. The wakeup itself lives only in the harness
process, so the daemon keeps every one it saw asked for, with its time and
prompt, on the volume: a harness that is alive fires its own and the daemon
only records it; a harness that was restarted has lost it, and the daemon
fires it as a prompt marked as a wake. Neither a pending wakeup nor a
standing cron lets the idle kill stop the harness; a cron survives a restart
in the harness's own files. The page shows a wake as a line, not a bubble:
nobody typed it.

**A subagent's work nests under the call that spawned it; a task is one
entry.** The adapter stamps every update a subagent produces with the id of
the Agent call that made it, and tells the client, when asked, about
background tasks as they spawn and settle. The daemon asks, keeps the stamp
on each tool event, streams a subagent's words as its activity rather than
the conversation's, and reads a finished subagent's bill from the trailer on
its report: tokens, tool uses, duration. The page gathers a subagent's calls
under it, says "Ran 2 subagents" where t3code does, and lists the fleet in
an Agents tab beside the terminal. A workflow appears as the task the
harness reports it as, with its state; its agents run inside the harness's
own runner and do not stream, so the task's summary is what the page has.
Every one of these calls goes through the gateway with the conversation's
id, so the ledger holds them all.

**Everything metered.** `model_calls` holds every call with its tokens and
the vendor's reported cost; `measure()` turns them into one `tokens` line per
model per window, and `usage` gained a `model` column for it. The cap is a
constant per org per month, checked at the gate from the same rows.

**The layout follows t3code, element by element.** t3code (MIT, the same
React, Tailwind v4 and Base UI stack as ours) was read in source: its thread
sidebar, chat header, messages timeline with work groups, composer, terminal
drawer and right panel. Its elements come in one at a time, each adjusted
here, on our own shadcn skin. Beautiful UI was considered for its harness
demo and dropped: nothing of it is used. What stands today is a first cut:
a sidebar of conversations, a header with the title and the terminal, a
reading column of prompts, streamed replies and tool rows, a composer with
the model picker, and a terminal pane.

**The fake is a fallback.** Without a model key the daemon runs
`fake-agent.mjs`, an ACP agent that answers every prompt with one tool call
and a sentence; the page and the pill say so; production refuses to start.
The smoke drives the whole loop against it.

**On a laptop the machine is local, and as real as a laptop allows.** A
machine on Fly cannot call a laptop back, and the agent needs the app for
its model, its configuration and its events. So `pnpm dev` runs the machine
as a process beside the app: the same daemon, the same harness, the same
gateway, one address. The harness gets the disk as its home and working
directory, its own config directory and temp on it, and none of the laptop's
environment. The disk lives in the laptop's scratch directory, outside the
checkout: the harness reads every `CLAUDE.md` and every git repository
above its working directory, and a disk inside the checkout handed it this
repo as the person's project. What a laptop cannot give is the Debian
image, root and the chroot; those are exercised on the preview, which has a
real address and real machines of its own. `COMPUTERS=fly pnpm dev` still makes real machines
from a laptop for work on the machine itself, knowing they cannot reach it.
A tunnel was built and removed: an address that changes on every start is
worse than none, and the preview already is the address.

**Deferred, on purpose.** The brain as an MCP server for the agent; waking
the machine itself for a wakeup: Fly suspends a machine a few minutes after
its last request, an agent mid-turn or a timer pending notwithstanding, so
a wakeup due after that fires only when something next asks for the machine.
The app holds every wakeup's time in the `ScheduleWakeup` event; a cron
that asks for the machine when one is due is the missing piece, metered and
capped like any other turn. Also seen on the preview: a harness resumed from
suspension can wait out a dead connection to the gateway for minutes before
its next call goes through. Images and files in prompts; an approvals
surface; reconciling `model_calls` against the vendors' invoices.

## Reconciled with the model door (2026-09-05)

A second design of the gateway, built apart, was folded in: a call is a row
before the vendor hears of it and settled with its tokens when the answer
ends, or when the reader leaves with what was reported by then, so no token
is bought without a row; a call the vendor refuses is dropped. Calls are
their person's to read, and the org sees each member's use through the
usage ledger. The machine's credential is its id and secret as one bearer
token, what Claude Code sends natively, and every shell on the machine
carries the gateway's address and the offered model, so `claude` in the
terminal is on the gateway with no sign-in. Production without a key boots
with no agent, as it boots without computers; outside production a pretend
model answers at the gateway so the terminal and the smoke work with nothing
spent. Kept from the first design: the catalog and its vendors, the cap in
dollars per org per month, the vendor's own price when it reports one, and
one usage line per model.
