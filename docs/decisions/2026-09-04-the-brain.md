# 2026-09-04 — the brain

Four decisions made while building `packages/brain`, and what was decided
against.

## Kinds and verbs are open; fields are rows, not columns

The previous repo let a user define a type and ran `ALTER TABLE` at request
time through a privileged executor, with a registry of generated tables.
Here a kind is a row with a description, and the fields it declares are rows
in `kind_properties`. Values stay in `records.props`. The write door validates
against the declaration and the read door filters and sorts by it, casting
the JSON text to the declared type, with names taken from the catalog and
values checked before the database sees them. A kind that declares nothing
accepts anything. Postgres's shape changes only in migrations.

A starter vocabulary installed into every org was built and then removed:
the agent is meant to find the best structure for a person, not inherit
ours. A brain starts empty. The seed defines the vocabulary its own records
use; product code that writes a kind it knows, like a note, defines that kind
on first use; the agent defines the rest. Writing an undefined kind or verb
is refused with a message that says so.

## Records belong to a person from the first migration

One person is an org of one today, which made it tempting to scope by org
only and add the person later. Rejected: adding a second person to an org
must not be a rewrite. Records, edges and events carry `person_id` beside
`org_id`, defaulted from a transaction setting, and their policies require
both. The vocabulary stays org-scoped. Making `person_id` nullable for
org-level records was considered and rejected: it would create one sharing
level, "everyone", as the only way to share, and every such row would need
reclassifying when real access control arrives. Ownership stays non-null;
visibility will be its own mechanism.

## A merge is an alias, not a rewrite

Merging two records sets `merged_into` on the loser and hides it. Its edges
stay where they are; reads follow the pointer. Unmerge clears it. Only
records of the same kind merge, a winner must be live, and both rows are
locked, so aliases never chain or cycle. Rewriting edges to the winner was
rejected because undoing it needs a journal of what moved.

## Edges carry detail

Edges have `props`, `confidence` and `occurred_at`, like records. The
sentence the product is built around, "these conversations weakened that
assumption, strongly, on Tuesday", is an edge with a strength and a time.
Writing an edge is an upsert: the same link again changes nothing.

## The brain is a mind, not a mirror

The first plan had an adapter per source that copied every message and
calendar entry into the brain as source records, with sync jobs and cursors,
and the agent deriving from those rows. Replaced before any adapter was
written. The brain is a knowledge graph of what a person means: who they
owe, what they believe, what they committed to, what changed. The agent reads
sources through Composio tools and writes conclusions; each rests on a stub
holding the app, its id and enough to cite it, never the body. It records
how far it has looked so refreshes are incremental, and what it learns on a
cache miss it writes.

Accepted with it: the graph is only as complete as the agent's attention,
re-deriving means re-fetching, cost moves from storage to tokens, and two
runs may differ but should converge, because the product is about judgment.
It removes a layer of code, keeps every app Composio reaches a source from
day one, and leaves a graph small enough to draw. The comment at the top of
the records table in `20260904_055950_brain.sql` describes the earlier plan;
an applied migration is not edited.

## Deferred, on purpose

Relevance or vector search: full-text is enough until a real question fails.
Sharing between people. Nested field types.
